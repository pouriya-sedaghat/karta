## Product decision to implement

The region is **Iran from raw OSM PBF**, with [Geofabrik's Iran page](https://download.geofabrik.de/asia/iran.html) selected as the raw-data distributor. The owner wants automatic publication after a complete file reaches the system, whether the file arrived online or was delivered locally during an internet outage. The difference is **intake and authorization**; after acceptance, both paths use the same existing private staging, complete PBF/region/provenance/timestamp validation, forward rule, storage check, isolated build, validation, audited pointer switch, retention and rollback policy.

Choosing Geofabrik also fixes the region's identity. Karta matches a snapshot to its region by the PBF header (or verified sidecar) box, to 1e-7°, so the Iran region box is the box of Geofabrik's Iran extract, and **both paths accept only that extract**. A manually delivered Iran PBF from another distributor, or a self-made clip, has a different box and is refused (`region_mismatch`) by design; accepting it needs a reviewed region-file change, not an intake option. If Geofabrik changes its Iran boundary, both paths refuse new files the same way until such a change; document that failure and its recovery.

**Online intake:** A controlled source bridge checks Geofabrik for a newer complete Iran PBF, obtains it within strict resource and destination bounds, verifies its identity and policy, records provenance, and publishes a Karta-compatible signed manifest and exact snapshot bytes. The manifest names the bridge's own immutable, content-addressed copy of the bytes it verified, never `iran-latest.osm.pbf` (whose bytes change with every update), so Karta never downloads from Geofabrik directly and Geofabrik serves each version to the deployment once. Karta's existing fetcher verifies the manifest with a pinned public key, downloads and checks the bytes, and hands the delivery to the publisher. The bridge holds the signing key; the fetcher and publisher never do. The bridge may be implemented as separable downloader and signer processes if that gives the key a materially smaller attack surface (decision 2). Geofabrik's page or co-hosted checksum is not itself the Karta signed manifest. Do not create or commit a production private key or silently select its custodian.

**Trusted local intake:** During an outage, an authorized operator delivers a complete Iran PBF, with the authenticated submission command or, where the host proves the writer boundary, into a protected local landing area. A bounded local intake component establishes that the copy is complete (decision 4), obtains the exact SHA-256, runs only advisory pre-checks that reuse the publisher's code, creates only an exact-digest authorization through a new narrow capability (decision 1), and hands the file to the publisher with the existing completion protocol. The publisher independently stages and verifies it; the intake needs no online signing key, no database credential and no route out. No per-file approval should be needed *after* the authorized operator's deliberate local delivery, but the delivery plan's rule that manual submissions keep per-digest pinning or authorization still holds: the intake automates that authorization, it does not remove it. This is an opt-in trust mode, off by default: write access to the protected landing area (like the intake's credential combined with write access to the inbox) is publication authority for any snapshot that passes the common checks, comparable to the signing key, and must be narrowly controlled, observable and documented. Keep the existing pin/per-digest authorization path available as an independent fallback, including when the bridge or local intake component is down. Do not make arbitrary `data/inbox` writes automatically trusted or silently broaden the existing policy.

The operator-facing goal is “deliver one complete PBF, then observe automatic processing.” **The authenticated submission command is required, not an alternative**: it is the fail-closed path wherever a landing area's writer boundary cannot be proven, it gives person-level attribution (one named credential per operator), and it uses the same narrow capability. The unattended folder watcher is an optional mode of the same component, enabled per deployment only after its preflight (decision 4) passes. A normal shared folder does not authenticate an operator. On a Windows-hosted VM in particular, hypervisor and host shared folders (for example vboxsf, vmhgfs-fuse, SMB/CIFS, 9p/drvfs) synthesize Unix owner and mode bits from mount options while the Windows host decides who can write, and they have weak inode, mtime and symlink semantics, which the inbox protocol already does not support (`docs/security.md`). Treat such a folder only as an **untrusted transport** from which the command copies; never use it as the landing area, the inbox, staging or a Docker volume. A trusted landing area is a directory on a VM-local POSIX filesystem written only through an authenticated channel (for example SFTP as a dedicated account). If the boundary cannot be enforced, fail closed and use the command.

Online enablement is a **deployment choice made once**, not a switch the operator must flip whenever connectivity changes. With the online source configured and running, transient loss of internet causes bounded retries and clear status; the active release and manual intake continue. On restoration, polling resumes. Offline-only deployments need no source bridge, trusted key or external runtime dependency.

## What the current code already decides

These facts constrain the design; the implementation must change them deliberately (ADR) or design around them.

- **Operator scopes.** `publish` covers authorize, revoke, activate and online pause/resume/retry; `status` reads status, audit and metrics; `rollback` and `cleanup` are separate. An unknown scope fails credential parsing, so a credentials file with a new scope stops an older publisher at start (a safe downgrade). Operator credentials are read only at publisher start: adding or removing one takes effect when the publisher restarts, which records a running publication `interrupted` (ADR 0005).
- **Authorizations.** One open authorization per region and digest; the region is the publisher's own; size and expiry are optional (expiry at most one year); an authorization is not single-use. `Authorize` with a different size, or over an expired row, **revokes the existing open row as `superseded`**, and `Revoke` closes by digest, not by row id. A narrow capability built on these unchanged could revoke or replace an operator's authorization.
- **When authorization is checked.** In `importer.Verify` on the staged copy, *after* the full PBF scan. For manual and command-line submissions it is **not checked again at the switch**; only signed online deliveries are (`onlineGate` inside `registry.Activate`, which with `require_operator_authorization` also refuses an operator authorization that expired during the build). A submission rejected as `unauthorized_digest` is re-evaluated when an authorization for exactly that digest and size appears.
- **Queueing.** The publisher scans and builds one submission at a time; a manual submission that arrives during another build is staged and verified only after that build ends (up to `KARTA_PUBLISH_TIMEOUT`, 6 h provisional). An interrupted submission is re-staged and re-verified on each retry (up to `KARTA_PUBLISH_MAX_ATTEMPTS`, 3).
- **Completion.** The inbox requires a `.ready` marker written last; ADR 0003 rejected “wait for a stable size” because a stalled copy looks stable. A PBF cut exactly between blobs passes the structural scan; today only the marker's independently obtained digest catches it.
- **Inbox exposure.** The inbox rejects symlinks, non-regular files and bad names and checks inode, size and mtime, but not the link count. Anyone who can write `data/inbox` can submit files; more than `KARTA_INBOX_MAX_ENTRIES` entries fails the whole inbox scan.
- **Labels.** Audit sources (`operator_api`, `inbox`, `cli`, `system`, `online`) and submission sources (`inbox`, `cli`, `online`) are database constraints: a new label such as `local_intake` is a registry migration (schema version 4) with its ADR. Recording the intake as the credential name through `operator_api` needs none.
- **Online.** The fetcher and publisher already persist the newest verified serial (fetcher state and `registry.source_state`), refuse a lower serial (`manifest_replayed`) or another envelope under a verified one (`manifest_conflict`), re-verify at the switch, and re-deliver held bytes when the delivered manifest lapsed and a newer serial for the same snapshot is served. `karta-sign` takes `--serial` from its caller, so serial persistence is new bridge work. Restoring Karta's registry pauses online activation (ADR 0005).

## Review decisions and implementation boundaries

1. **Local trust model.** Propose a minimal, explicit trust model for the landing area and the component that authorizes a digest: privileges, credential scope, filesystem/mount requirements, isolation from the online signer, audit identity and error recovery. The current operator `publish` scope also permits release activation, digest revocation and online-policy changes: **do not give that broad token to an unattended local watcher**, nor to operators who only deliver files.
   - *Capability.* Add an authorization-only scope (or a comparably narrow mechanism) whose single action creates an authorization the publisher bounds: exact digest, **required** size, the publisher's own region (the request names the region it expects and is refused if it differs), and a **required** expiry no later than a publisher-side cap. It must not revoke, supersede or extend an authorization it did not create (the supersede and revoke-by-digest behavior above must not apply to it), may close only its own authorizations (by id), and may hold at most a small configured number of open ones. Prove that it cannot activate/rollback/clean up releases, change online policy, revoke others' authorizations or reach any other route. If the intake must learn its submissions' outcomes, give it a narrow read of its own records, or document that a `status` grant lets it read all operator status.
   - *Process.* The intake runs non-root with a read-only root filesystem, no capabilities, no database credential, no signing key and no route out (only the `operator` network to the publisher), with memory, CPU and PID limits; the command runs as a one-off client (like `operator-cli`) with only the mounts it needs.
   - *Expiry and revocation during a long import.* Recommended default (owner confirms): inside the pointer transaction, re-evaluate the basis that admitted the submission (the pin in the region file read then, or an unexpired, unrevoked authorization), as the online gate already does. A refusal leaves the release `ready`, the pointer unchanged and an audited `rejected` outcome; a fresh authorization and resubmission then activates the ready release without rebuilding. The validity cap must therefore cover a wait behind a running build, the publication itself and the allowed interrupted retries: derive it from `KARTA_PUBLISH_TIMEOUT` and `KARTA_PUBLISH_MAX_ATTEMPTS` and record the margin; it names bytes the trusted channel already accepted, so a longer validity widens little. Applying the switch re-check to every authorization-admitted manual and command-line publication (a revocation then stops a running publication) is a tightening of existing behavior: record it as such. The alternative, judging expiry only at verification, must say how a retried interrupted submission keeps its authorization. An authorization that expired unused is not renewed automatically; the operator delivers again.
   - *Ordering and orphans.* Hash the complete copy → create the authorization → hand off the files and write the `.ready` marker last, each by atomic rename. Authorizing first avoids a wasted staging copy, a full scan and a `rejected` record (authorization is checked after the scan). After a crash between authorization and marker, the restarted intake completes the handoff only if the landing file is unchanged and still has that digest, otherwise closes its own authorization; an intake that never returns leaves it to expire. The intake closes its own authorization once the submission it admitted is final.
   - *Identity.* Do not assume that SHA-256, a `.ready` marker or file ownership authenticates a writer. If a copied file cannot identify the individual, audit the trusted local channel (credential name, landing owner UID, file name, size, mtime, digest) and state that limit; offer the authenticated command when person-level attribution is required. Root and members of the `docker` group can publish regardless of these controls (Docker access is root-equivalent): document them as inside the boundary.
   - *Turning it off.* Document how to stop the intake at once: stop the service, close its open authorizations, remove its credential. Removing a credential currently restarts the publisher and interrupts a running build; either accept and document that, or make operator credentials reload like `metrics_tokens`.
   - *Challenge for the ADR.* The intake token plus write access to `data/inbox` is itself publication authority, so it is a secret like a signing key. Compare this design with a publisher-native trusted landing feed that needs no token, and justify the choice; the narrow scope is needed for the authenticated command either way.
2. Choose and document the bridge topology, signing-key custody and operational handoff as **configurable** design: a separate bridge host (the producer model of ADR 0004) or a bridge co-located on the Karta host in its own containers. When co-located, the bridge downloader is the only container with an internet route, and the fetcher needs only a private route to the bridge's HTTPS endpoint (`allowed_networks`, `ca_file`), so remove the fetcher's internet egress in that topology. A separate signer process protects the key from exfiltration by a compromised downloader, not from misuse (the downloader can still ask for signatures); it is worth its cost only if the signer opens no connections, reads the bytes it signs itself (hash and header), logs every signature and refuses a different snapshot that is not newer than the last one it signed. Otherwise one bridge process with no inbound listener beyond read-only serving is simpler; decide in the ADR. The bridge should sign only a snapshot that passed its bounded acquisition and the structural, region and timestamp checks `karta-sign` runs, not every file placed in a writable directory. CI keys are generated at test time; a VM test key is generated on the VM, labelled as test material and never reused; the production key and its custodian are an owner decision. Karta must independently verify the signed manifest and staged PBF, including at activation, as it does now. Keep any bridge network reachability outside the public API request path and keep database credentials out of the bridge.
3. Define the online new-version algorithm before coding: the official Iran PBF location and any metadata used as a *hint*, polling interval and backoff, exact-byte SHA-256, size and PBF data timestamp, source/provenance record, monotonic manifest serial, deduplication, conditional requests if safe, and handling a changed digest with equal/older data time (do not sign it; report it, since Karta would refuse it as `not_newer` or `older_than_active`). Download a full file only when a hint changes, at most once per version. Resume an interrupted download only with a strong validator (`If-Range`), otherwise restart: `iran-latest` can be replaced during a transfer. Confirm and record Geofabrik's current download terms, send a descriptive `User-Agent`, honor `429`/`503` and `Retry-After`, and keep the poll interval in hours unless the owner decides otherwise. A file name, `Last-Modified`, ETag or checksum alone is not publication authorization; record Geofabrik's `.md5` as distributor metadata only.
   - *Serial and state.* Persist (write, fsync, rename) the next serial and the exact signed asset (digest, size, data timestamp, envelope digest) before making a new manifest visible. Derive each serial as at least the issue time in Unix seconds (`max(last + 1, issued_at)`), so a bridge restored from older state or backup cannot go below a serial it issued or Karta recorded unless its clock went backwards (signing is rare, so serials do not run ahead of the clock); refuse to sign when the clock is earlier than the last `issued_at`. Seconds also keep the fetcher's 12-digit delivery names (`s%012d`) in serial order; milliseconds would not.
   - *Publication.* Write the asset under a content-addressed name (temporary file, fsync, rename, fsync of the directory), then replace the manifest the same way, so a reader sees the old or the new manifest and never a partial asset. Serve `Range` requests with a strong ETag so the fetcher's verified resume works. Keep an asset until every manifest naming it has expired.
   - *Validity.* Size `max_manifest_validity` above the download time plus a queue wait plus `KARTA_PUBLISH_TIMEOUT`, so an Iran build normally switches on its first delivery. Re-sign the held asset under a new serial no later than halfway through the current manifest's validity, independently of Geofabrik's reachability; the fetcher's existing re-delivery then activates the ready release when a manifest lapsed during an outage or build. Re-signing never makes old data look fresh, because staleness comes from the data timestamp.

   Use full PBF snapshots; diff replication remains an optional later extension. Keep the raw URL and update policy reviewable and configurable where appropriate.
4. Define manual completion and resubmission rules: partial copy, crash before/after marker, a file changing during the copy, non-regular files/symlinks/hard links, duplicate digest, older timestamp, simultaneous online and manual arrivals, an explicit rollback, rejection, disk full and retry. Preserve current manual-first scan order and build lock unless a written ADR explains a safe change. A manual candidate must never silently overwrite a newer active release; a failed candidate never changes the active pointer.
   - *Completion signal.* Never infer completion from a stable size alone (ADR 0003). The command knows when its own copy ends. The watcher needs an independent signal: by default a checksum file written after the PBF (`NAME.osm.pbf.sha256`; accept bare hex in either case, `sha256sum` lines and CRLF, as Windows tools produce), optionally the distributor's `.md5` as a check against accidental truncation only. Without one, a copy cut exactly between blobs passes the structural scan and the intake's own digest, and only the region's row-count gates stand in the way; another signal needs an ADR argument. Ignore temporary names (dot files, `.part`, `.filepart`) and apply a settle interval.
   - *Landing preflight.* Refuse, and report why: a symlinked landing directory or parent, FIFOs, devices and directories, a link count other than 1, files not owned by the landing owner, a landing directory or parent writable by group or others beyond the configured writer group, and a filesystem that is not a local POSIX filesystem (shared-folder, FUSE or network types). Provide a `check` command that runs the same preflight and fails closed, so the inspection on a host such as the VM is reproducible, and run it before every scan, not only at start.
   - *Handoff.* Name handoff files uniquely (digest prefix and time) and never overwrite. Handing off into the shared `data/inbox` lets anyone who can write it delay the trusted path (a flood beyond `KARTA_INBOX_MAX_ENTRIES` fails the whole scan); either document that or give the intake its own handoff directory, read-only to the publisher, with the inbox protocol and manual-class scan order (owner decision).
   - *Rollback.* A rollback pauses automatic activation of online snapshots (ADR 0004). Decide whether it also pauses automatic activation of watcher submissions; while paused they would be built and kept `ready`. Recommendation: pause the watcher, so unattended automation never undoes an operator's rollback, and leave command and direct inbox submissions unchanged.
5. State exactly what the common path shares and what must differ: authorization metadata, source/provenance labels and possibly source-specific freshness policy are different; PBF/region checks, build and switch remain common. The command and the watcher share one implementation. Avoid building a second importer or granting the source bridge direct database access.
6. A full-Iran region file is needed. Derive its box and initial pinned digest from a **fixed, recorded** Iran PBF with `karta region-draft`; do not scale Chitgar counts or invent search/tile acceptance values. The owner supplies that file out of band, as for Chitgar (for example `iran-260927.osm.pbf`, whose size and SHA-256 the Chitgar sidecar records as an unverified claim); do not download one. Until it is supplied, the Iran region file and its acceptance checks stay open and the work proceeds on fixtures. Fill acceptance checks from a measured Iran import and retain the digest and verified provenance. Do not silently replace a pinned test snapshot with a moving `latest` alias.
7. Keep limits explicit and measurable: download and staging sizes, disk reserves for simultaneous candidate and retained releases, memory/CPU, worker counts, publication deadline, request frequency and retry storms. The ~230 MB compressed PBF (229,580,914 bytes recorded, unverified, for the 2026-09-27 file) is not a database or temporary-storage budget. Count every full copy per filesystem: bridge store (current asset and any still referenced), fetcher outbox (two deliveries and one partial), landing area, handoff or inbox, publisher staging, the candidate database and the active and retained releases. Move by rename within one filesystem rather than copy where the trust boundary allows; the publisher's private staging copy stays. Import, signing and hashing must not block serving; avoid needless extra full-file copies where a safe streaming or atomic handoff suffices. A dynamically growing virtual disk can report free space its host does not have; capacity checks inside a VM do not cover that. Values for a future production host stay provisional until measured there.
8. Update the operator API/status, metrics and alerts only as needed to distinguish bridge health, last source check, accepted digest/data age, local intake state (last landing scan, preflight result, files waiting and why, open authorizations, last outcome), rejected submissions and active-release freshness. Bridge health as Karta sees it is the fetcher's existing report plus data age; a co-located bridge may expose its own status, but do not add a Karta-to-bridge connection for monitoring. An online check must not make old active data appear fresh. Preserve scoped credentials and avoid sensitive/high-cardinality labels (no file names, paths or digests as labels). Document error messages and a recovery action for each failure.
9. Preserve OSM attribution and a clear chain of provenance: exact source URL/file, observation and data timestamps, digest, any distributor metadata, bridge identity and signing key id. Label a manually supplied file as a manual submission through the named channel; do not attribute it to Geofabrik merely because it is an Iran PBF, because its sidecar or an operator says so, without supporting evidence (sidecar source claims stay claims, as today). A manual digest equal to one the bridge already signed may be linked to that record as evidence. A valid bridge signature proves the bridge approved those bytes under its policy; it is not independent proof that OSM facts are correct or that Geofabrik signed the file.

## Acceptance evidence

- Fixture CI uses a controlled HTTPS Geofabrik stand-in, throwaway signer/key and tiny PBFs. For the bridge's own acquisition leg, prove first publication, newer version, unchanged version without repeat download or build, changed bytes with stale/equal timestamp, invalid/corrupt/oversized input, TLS/destination/redirect refusal, missing source, `iran-latest` replaced during a download, download interruption and recovery, rate and disk limits, signer failure and signing with two keys during a rotation. Crash after the asset is written but before manifest promotion, restore the bridge from older state, and re-sign the same bytes after expiry; no partial asset may be advertised and no serial reused for different bytes or lowered below one issued or recorded. Reuse, rather than duplicate, the Stage 3 fetcher and publisher suites for bad/expired/revoked signatures, serial replay and destination policy, and run the bridge-to-publisher path end to end at least once. No CI test depends on live Geofabrik.
- With the network disconnected, serve tiles/search from the current release; deliver a newer PBF through the authenticated command and through the protected watcher, and observe automatic publication without online signer or fetcher. Exercise partial files, a copy cut exactly at a blob boundary (refused without a valid checksum), a missing or wrong checksum, a file modified after the intake hashed it (the publisher refuses; pointer unchanged), unauthorized writers or insecure directory permissions, each preflight refusal, symlinks/FIFOs/hard links, interrupted copy, duplicate/older input, a local-intake crash before/after digest authorization and marker, an authorization expiring while queued behind a long build or across an interrupted retry, a revocation between verification and the switch (release stays `ready`, pointer unchanged, audited), a rollback followed by a watcher delivery (per decision 4), a flooded `data/inbox` (per the handoff decision), bridge outage, publisher restart and normal direct manual fallback. Prove that the intake's credential gets 403 on every other operator route and cannot revoke, supersede or extend another principal's authorization, exceed its open-authorization limit or omit size and expiry; that orphan authorizations are closed or expire; that the same post-intake publication checks run; and that failures leave the pointer unchanged.
- Under concurrent map/search requests, exercise slow download, local delivery, build, switch and rollback, reusing the existing serving-during-publication harness. Confirm pinning, no unexpected request failures, no duplicate build, and bounded time/memory/disk; record actual figures and test environments rather than claiming Iran or production capacity from fixtures.
- If the owner opens a separate Claude Code session with access to the Windows-hosted VM, first present a concrete, reviewable test plan: backups and current VM state, exact fixed PBF and digest, hypervisor and how files reach the VM, the filesystem type of the checkout, `data/inbox`, the landing area and Docker volumes, free disk inside the VM and on the Windows host (and whether the virtual disk is dynamically growing), CPU/RAM, time synchronization and a clock check across a suspend and resume, commands, timeouts, rollback and artifact locations. Run the landing preflight before enabling the watcher there; if it fails, use the command only. Then a **full-Iran VM rehearsal** may measure publication, database and staging size, latency, backup/restore, alerts and failures. Label it as tier C evidence for that VM only, never tier D production-host acceptance. Do not access that VM or download a replacement Iran snapshot without the owner's authorization for the test plan.
- Run relevant race/unit, script, promtool, integration, browser and disconnected tests; static/security checks and CI on the final implementation head. Add targeted regression tests for the new local authorization boundary and bridge behavior, including negative controls that fail before the fix. Review the actual source and deployment files, not only test outcomes.

## Owner decisions

Each is open until the owner answers it or delegates it to the implementation ADR:

1. Stage number and name in the delivery plan, and what happens to the current “Stage 5: optional extensions” entry.
2. Bridge topology (separate host or co-located), the production signing-key custodian, and when a deployment enables online updates (off until then; local delivery needs none of them).
3. Per deployment: command only, or command plus watcher; who is in the landing area's writer set; whether person-level attribution is required for every local delivery; and whether the watcher's checksum file (decision 4) is an acceptable cost of “deliver one file”.
4. Authorization semantics: re-check at the switch including expiry (recommended) or expiry at verification only; the validity cap; whether the switch re-check also applies to existing `publish`-scope authorizations and region pins.
5. Whether a rollback pauses watcher auto-activation, and handoff into the shared `data/inbox` or a dedicated directory.
6. Operator credential changes by publisher restart (current) or by reload.
7. Geofabrik poll interval, `max_manifest_validity` and re-sign interval, and the acceptable data age (`KARTA_DATA_STALE_AFTER`), which is already open.
8. The fixed Iran PBF to supply out of band for the region file and its measured acceptance checks.
9. Authorization of a VM test plan in a separate session. The production host, service objectives and other Stage 4 owner inputs stay open as listed in `docs/operations.md`.
