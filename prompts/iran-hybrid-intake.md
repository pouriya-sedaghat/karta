## Product decision to implement

The region is **Iran from raw OSM PBF**, with [Geofabrik's Iran page](https://download.geofabrik.de/asia/iran.html) selected as the raw-data distributor. The owner wants automatic publication after a complete file reaches the system, whether the file arrived online or was delivered locally during an internet outage. The difference is **intake and authorization**; after acceptance, both paths use the same existing private staging, complete PBF/region/provenance/timestamp validation, forward rule, storage check, isolated build, validation, audited pointer switch, retention and rollback policy.

**Online intake:** A controlled source bridge checks Geofabrik for a newer complete Iran PBF, obtains it within strict resource and destination bounds, verifies its identity and policy, records provenance, and publishes a Karta-compatible signed manifest and exact snapshot bytes. Karta's existing fetcher verifies the manifest with a pinned public key, downloads and checks the bytes, and hands the delivery to the publisher. The bridge holds the signing key; the fetcher and publisher never do. The bridge may be implemented as separable downloader and signer processes if that gives the key a materially smaller attack surface. Geofabrik's page or co-hosted checksum is not itself the Karta signed manifest. Do not create or commit a production private key or silently select its custodian.

**Trusted local intake:** During an outage, an authorized operator places a complete Iran PBF into an explicitly protected local landing area. A bounded local intake component verifies that the copy is complete, obtains the exact SHA-256, applies the manual-source policy and the existing input checks as appropriate, creates only an exact-digest authorization (or an equivalently narrow audited capability), and hands the file to the existing **manual** inbox using an atomic completion marker. The publisher independently stages and verifies it; the local intake component does not need an online signing key. No per-file approval should be needed *after* the authorized operator's deliberate local delivery. This is an opt-in trust mode: write access to the protected landing area is publication authority and must be narrowly controlled, observable and documented. Keep the existing pin/per-digest authorization path available as an independent fallback, including when the bridge or local intake component is down. Do not make arbitrary `data/inbox` writes automatically trusted or silently broaden the existing policy.

The operator-facing goal is “deliver one complete PBF, then observe automatic processing.” An authenticated submission command is acceptable as a safer implementation if a plain folder watcher cannot prove the landing area's writer boundary on the chosen host; explain that tradeoff in the brief review rather than pretending a normal shared folder authenticates an operator. On the Windows-hosted test VM, inspect the actual shared-folder and Unix permission behavior before enabling any trusted-folder policy. If the boundary cannot be enforced, fail closed and use the authenticated submission path.

Online enablement is a **deployment choice made once**, not a switch the operator must flip whenever connectivity changes. With the online source configured and running, transient loss of internet causes bounded retries and clear status; the active release and manual intake continue. On restoration, polling resumes. Offline-only deployments need no source bridge, trusted key or external runtime dependency.

## Review decisions and implementation boundaries

1. Propose a minimal, explicit trust model for the local landing area and the component that authorizes a digest: privileges, credential scope, filesystem/mount requirements, isolation from the online signer, audit identity and error recovery. Do not assume that SHA-256 or a `.ready` marker authenticates a writer. If a copied file cannot identify the individual, audit the trusted local channel and state that limit; offer the authenticated command when person-level attribution is required.
2. Choose and document the bridge topology, signing-key custody and operational handoff as **configurable** design. The bridge's signer should sign only a snapshot that passed its bounded acquisition and policy checks, not every file placed in a writable directory. Karta must independently verify the signed manifest and staged PBF, including at activation, as it does now. Keep any bridge network reachability outside the public API request path and keep database credentials out of the bridge.
3. Define the online new-version algorithm before coding: the official Iran PBF location and any metadata used as a *hint*, polling interval and backoff, exact-byte SHA-256, size and PBF data timestamp, source/provenance record, monotonic manifest serial, deduplication, conditional requests if safe, and handling a changed digest with equal/older data time. A file name, `Last-Modified`, ETag or checksum alone is not publication authorization. Use full PBF snapshots; diff replication remains an optional later extension. Keep the raw URL and update policy reviewable and configurable where appropriate.
4. Define manual completion and resubmission rules: partial copy, crash before/after marker, a file changing during the copy, non-regular files/symlinks/hard links, duplicate digest, older timestamp, simultaneous online and manual arrivals, an explicit rollback, rejection, disk full and retry. Preserve current manual-first scan order and build lock unless a written ADR explains a safe change. A manual candidate must never silently overwrite a newer active release; a failed candidate never changes the active pointer.
5. State exactly what the common path shares and what must differ: authorization metadata, source/provenance labels and possibly source-specific freshness policy are different; PBF/region checks, build and switch remain common. Avoid building a second importer or granting the source bridge direct database access.
6. A full-Iran region file is needed. Derive its box and initial pinned digest from a **fixed, recorded** Iran PBF with `karta region-draft`; do not scale Chitgar counts or invent search/tile acceptance values. Fill acceptance checks from a measured Iran import and retain the digest and verified provenance. Do not silently replace a pinned test snapshot with a moving `latest` alias.
7. Keep limits explicit and measurable: download and staging sizes, disk reserves for simultaneous candidate and retained releases, memory/CPU, worker counts, publication deadline, request frequency and retry storms. The ~200 MB compressed PBF size is not a database or temporary-storage budget. Import, signing and hashing must not block serving; avoid needless extra full-file copies where a safe streaming or atomic handoff suffices. Values for a future production host stay provisional until measured there.
8. Update the operator API/status, metrics and alerts only as needed to distinguish bridge health, last source check, accepted digest/data age, local intake state, rejected submissions and active-release freshness. An online check must not make old active data appear fresh. Preserve scoped credentials and avoid sensitive/high-cardinality labels. Document error messages and a recovery action for each failure.
9. Preserve OSM attribution and a clear chain of provenance: exact source URL/file, observation and data timestamps, digest, any distributor metadata, bridge identity and signing key id. A valid bridge signature proves the bridge approved those bytes under its policy; it is not independent proof that OSM facts are correct or that Geofabrik signed the file.

## Acceptance evidence

- Fixture CI uses a controlled HTTPS Geofabrik stand-in, throwaway signer/key and tiny PBFs. Prove first publication, newer version, unchanged version without repeat build, changed bytes with stale/equal timestamp, invalid/corrupt/oversized input, TLS/destination/redirect refusal, missing source, bad/expired/revoked signature, serial replay, download interruption and recovery, rate and disk limits, signer failure and key rotation. No CI test depends on live Geofabrik.
- With the network disconnected, serve tiles/search from the current release; deliver a newer PBF through the protected local intake and observe automatic publication without online signer or fetcher. Exercise partial files, unauthorized writers or insecure directory permissions, symlinks/FIFOs, interrupted copy, duplicate/older input, a local-intake crash, bridge outage, publisher restart and normal direct manual fallback. Prove the same post-intake publication checks and that failures leave the pointer unchanged.
- Under concurrent map/search requests, exercise slow download, local delivery, build, switch and rollback. Confirm pinning, no unexpected request failures, no duplicate build, and bounded time/memory/disk; record actual figures and test environments rather than claiming Iran or production capacity from fixtures.
- If the owner opens a separate Claude Code session with access to the Windows-hosted VM, first present a concrete, reviewable test plan: backups and current VM state, exact fixed PBF and digest, free disk/CPU/RAM, commands, timeouts, rollback and artifact locations. Then a **full-Iran VM rehearsal** may measure publication, database and staging size, latency, backup/restore, alerts and failures. Label it as evidence for that VM only, never tier D production-host acceptance. Do not access that VM or download a replacement Iran snapshot without the owner's authorization for the test plan.
- Run relevant race/unit, script, promtool, integration, browser and disconnected tests; static/security checks and CI on the final implementation head. Add targeted regression tests for the new local authorization boundary and bridge behavior, including negative controls that fail before the fix. Review the actual source and deployment files, not only test outcomes.
