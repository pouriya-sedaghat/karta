# Claude Code prompt: phase 1

Implement only Stage 1 from `docs/delivery-plan.md` in the GitHub repository `pouriya-sedaghat/karta`. Read `README.md`, `docs/architecture.md`, and `docs/delivery-plan.md` before editing. Work on a feature branch and open a PR against `main`. Do not merge. If the repository has no baseline commit yet, report that prerequisite instead of creating an unrelated history.

Goal: deliver a small but real, reproducible offline vertical slice for **map display and named-place/POI search**, using one consistent OSM snapshot. Do not implement online polling, automatic/manual inbox ingestion, diff replication, release switching, routing, or address-level geocoding in this PR. Preserve interfaces and database boundaries so Stage 2 can add immutable releases without rewriting consumers.

Requirements:

1. Build a self-hosted stack with PostgreSQL/PostGIS, `osm2pgsql` **flex** configuration for the data layers required by a simple vector map and named places/POIs, a tile serving path (Martin or a reasoned equivalent), a small HTTP API, and a minimal MapLibre integration example. Choose one maintainable API implementation language and explain it in the PR. Pin dependencies/container versions; do not rely on `latest` tags.
2. Define a documented, versioned contract for `/v1/manifest`, `/v1/search`, `/v1/releases/{release_id}/style.json`, and `/v1/releases/{release_id}/tiles/{z}/{x}/{y}.pbf`, with live/ready health endpoints. `release_id` must be a stable identifier derived from validated source metadata/content, even while Phase 1 has only one active release. Search responses include coordinates, stable OSM identifier/type if available, display name, category, and release ID. Bound `q` and `limit`; use parameterized SQL. Search supports UTF-8 and does not discard `name:fa`. Scope search to place names/POIs and say so explicitly in docs.
3. Supply a tiny deterministic OSM fixture or a documented fixture-generation procedure whose inputs are committed and whose license is recorded. Include at least one Persian named place, an English name, a road, and a water feature. Build the candidate data solely from that fixture in local integration tests. Keep bulky PBFs and database files out of Git. Do not make tests depend on a live internet download.
4. Create a simple basemap style with locally served style JSON, glyphs/fonts, sprites if used, and JS/CSS. Demonstrate that the test fixture produces at least one visible road, water feature and label. Provide OSM attribution and ODbL link in the demo. No use of OSM public tile or Nominatim servers; no external CDN or font fetches after setup.
5. Structure the code so the API can select a release-specific read-only database/tile source per request in Stage 2. Serving must not write into its source database. Put secrets in example environment configuration, never in source. Document bootstrap, explicit fixture import, readiness, normal startup, reset, and a simulated disconnected run. A running service must not require network merely to keep answering requests.
6. Write focused integration tests for importing the fixture, expected search of Persian and English names, release ID in responses, a decodable nonempty tile with expected layers/features, local style and asset URLs, and offline request serving after containers are initialized. Keep tests proportional; report any case blocked by unavailable local Docker/runtime honestly.

Acceptance: give exact reproducible commands and expected observable results. In the PR description, include an architecture sketch, file-by-file summary, commands actually run and their outputs, license/attribution notes, known gaps, resource assumptions, and why your choices allow Stage 2 to stage and atomically switch complete releases. If any requirement cannot be met, say exactly what is missing instead of claiming completion. Request code review when ready.
