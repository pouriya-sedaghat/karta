# Claude Code prompt: Stage 3 online updates

Implement Stage 3 from `docs/delivery-plan.md` in `pouriya-sedaghat/karta`. Start from updated `main` after the Stage 2 CI repair (PR #4, merge commit `43ffc9b` or later). Read the architecture, Stage 2 ADR, runbook, security model, region configuration, publisher and registry code, and public/operator OpenAPI contracts before changing code. Create `feature/phase-3-online-updates` and a draft PR against `main`. Do not merge, deploy, or access an owner-controlled host. Stage 3 has not yet been implemented.

Deliver the complete bounded capability: a configured HTTPS source is polled, a newer trustworthy complete snapshot is downloaded within strict resource limits, and the existing Stage 2 validation/build/activation path publishes it while the active release continues serving. A failed poll, download, or import never changes the active release or blocks manual offline publication. Preserve the versioned public API, release pinning, rollback, and operator security boundaries. Do not advertise online updates until the capability and its tests pass.

1. **Source and trust policy.** Make the source opt-in and configurable per deployment or region; no hard-coded production URL or implicit public OSM service. Specify one concrete, reviewable trust mechanism for unattended updates, such as a manifest signed by a pinned public key, with a verified digest and provenance bound to the intended region and snapshot. Document key rotation and failure behavior. Do not let a checksum downloaded from the same untrusted location silently bypass Stage 2 digest authorization. Reject unexpected schemes, destinations, redirects, oversized metadata, malformed manifests, and stale or conflicting source claims. Keep credentials out of Git, logs, request URLs, and the public API. Record the trust decision in an ADR and threat model.
2. **Poll and download.** Put all network traffic in the publisher's update path, never in public request handling. Bound connection and total time, bytes (including unknown-length and decompressed data where applicable), concurrent work, disk space, and retry attempts. Use TLS verification and a constrained destination policy that resists redirects and address changes to local/private services. Download to private staging, hash the bytes, verify the trusted metadata and provenance, then hand the exact completed file to the shared publication path. An interrupted transfer must be discarded or resumed only with a verified byte identity; never expose partial input as ready.
3. **Recovery and coexistence.** Persist enough source state to make duplicate digests idempotent across restarts and to recover a crash during poll, download, validation, build, or switch. Use bounded backoff with jitter and an operator-visible next attempt. Define a deterministic rule for simultaneous manual and online candidates: the existing timestamp, digest, and compare-and-swap rules still apply; an explicit operator switch or rollback is not overwritten by an online build that started earlier. Provide an operator pause/resume policy for automatic activation if needed, with audit records for changes and refusals. Manual import must remain usable with the network disconnected and the online source failing.
4. **Freshness and observability.** Expose the last successful check, verified source timestamp/digest, last attempt/error, next attempt, active data age, and a configured staleness threshold through operator status and suitable metrics. Extend the manifest's freshness fields only with documented additive API changes; never claim that a poll succeeded because the old release still serves. Keep source failures out of public request latency and avoid leaking sensitive upstream details. Update OpenAPI, README, runbook, configuration examples, ADR, and security documentation.
5. **Acceptance tests.** CI must use committed small fixtures and a local controlled HTTPS server, with no live external download. Exercise a successful newer online snapshot, duplicate and older inputs, invalid signature/digest/provenance, redirects and disallowed destinations, size and timeout bounds, broken transfers, network loss, retries/backoff, crash/restart at critical transitions, simultaneous manual and online submissions, rollback during a build, pinning, cleanup, and offline manual import while the source is unavailable. Keep serving map/search load during a slow download and activation; verify no request failures attributable to the update. Include browser and disconnected-network regression tests, lint/security/race gates, and reproducible resource measurements.

The owner has not yet selected a production HTTPS provider or permitted update lag. Keep both explicit configuration decisions, use the controlled source for acceptance, and report exactly what remains before operating online against a real provider. Do not substitute a random current extract or claim target-host validation. The PR description must include actual commands and outcomes, state transitions, failure recovery, trust boundaries, changed behavior, and known limits. Leave the PR draft for independent review if a Stage 3 acceptance gate is unmet.
