# Claude Code prompt: Stage 4 operations and capacity

Implement Stage 4 from `docs/delivery-plan.md` in `pouriya-sedaghat/karta`. Start from updated `main` after the Stage 3 merge (`2b93409` or later), not from the closed PR #6 branch. Read the architecture, delivery plan, ADRs 0002–0004, security model, runbook, Compose files, release registry and publisher/importer code, and public/operator OpenAPI contracts before changing code. Create a new Stage 4 branch and a **draft** PR against `main`. Do not merge it or claim production readiness. The owner previously ran Stages 1–2 on a local VM; Stage 3 has passed fixture-based CI but has not run on that VM or a real provider.

Stage 4 is the complete operational and capacity gate for the **selected** region, source and host. Keep Stage 3's online updates off by default. Do not select a production provider, generate a production signing key, set an acceptable data age or traffic/SLO target, or deploy to the owner's VM on the owner's behalf without the required owner inputs and access. Make every incomplete target-environment gate conspicuous in the draft PR; local fixture results are preparatory evidence only. Do not substitute Chitgar measurements for the production capacity claim.

1. **Deployment and trust inventory.** Document the target topology, version-pinned images and upgrade path, exposed interfaces/TLS and network egress, runtime user/volume permissions, resource quotas, disk placement and capacity, and the identities that can read credentials or write inbox/outbox/config. Audit least privilege for API, publisher, fetcher, importer, database, operator and backup roles. Verify that production secret distribution avoids the development `./secrets` assumptions. Define and rehearse credential and Ed25519 signing-key rotation, including overlapping key windows, revocation, rollback and loss of the key; never commit a private key or raw token. A signed manifest is required for unattended publication; a provider's checksum alone is not authorization. Record the selected source's direct HTTPS reachability, or implement and test a constrained proxy path before relying on one.
2. **Bounded publication.** Investigate the missing whole-publication deadline noted when PR #6 was closed: `RunInbox` calls `ScanOnce` with its long-lived service context, and `runOsm2pgsql` uses `exec.CommandContext` without a process-group cancellation policy. Set a configurable, measured whole-job budget and make cancellation stop all importer descendants without hanging on inherited stdout. Preserve cleanup and audit on timeout/crash, keep the active release serving, and prove a later retry can proceed. Exercise an importer that forks a child which retains the output pipe, plus a slow SQL/build phase and graceful shutdown. Do not copy PR #6 wholesale or assume its implementation is correct.
3. **Monitoring and response.** Supply deployable scrape/alert rules and a documented response for readiness, active release, API errors/latency, resource saturation, disk and WAL growth, publication duration/failures, fetcher state age and **active data age**. A recent successful poll must not mark old data fresh. Restrict the operator metrics endpoint with a scoped monitoring credential and TLS at any non-loopback exposure; avoid high-cardinality or sensitive labels. Test alert expressions against synthetic fresh/stale, paused and failed-source scenarios, and verify a stopped fetcher is observable.
4. **Backup and recovery.** Define consistent backups for registry, release databases, required volumes/config and offline-held secrets, plus an explicit restore order. Protect backups and test restoring to a fresh host or isolated stack. Verify active pointer, retained/pinned releases, audit history, online anti-replay state/outbox, read-only serving, and key/token access after restore. Explain the behavior if fetcher state is lost or unreadable: never silently reset an undelivered verified serial. Establish and measure recovery time and data loss against owner targets. Rehearse database loss/corruption, disk exhaustion during import and normal serving, failed upgrade, rollback and cleanup without touching the actual VM until the rehearsal plan is approved.
5. **Capacity and fault rehearsal.** On the selected host and region, record hardware, Docker/PostGIS versions, PBF digest/provenance, configured concurrency, disk/RAM/CPU peak, import time, candidate/active/retained/pinned storage, API QPS and latency distribution, errors and availability under sustained map/search load. Include concurrent slow download/build/switch and pinned clients, network outage, restart and rollback. Derive an explicit capacity margin and safe thresholds from measurements. Separate CI fixture, real Chitgar smoke, and production-region results. If the final geography, QPS, availability or update-lag objectives are undecided, measure provisional scenarios and keep the final gate open.
6. **License, documentation and acceptance.** Audit ODbL attribution and derivative-data obligations, bundled fonts and MapLibre licenses, third-party images/components and data provenance. Update the runbook with exact bootstrap, upgrade, backup/restore, token/key rotation, monitoring, incident and rollback commands; keep OpenAPI and security documentation aligned with any behavior changes. Add meaningful unit/integration/fault tests for code changes and run existing race, static/security, fixture integration, browser, prefix and disconnected-network gates. Record commands, results and measured limits in the PR. A passing CI run alone does not satisfy Stage 4.

Before target-environment work, obtain the owner's choices for: production geography and PBF source; signed-manifest provider or extraction-time signer and **private-key custodian**; acceptable active-data age; QPS/concurrency and availability/latency objectives; VM specifications, storage/backup destination, recovery objectives, network/proxy/TLS topology and operator access. Ask for access through the agreed secure channel only when a concrete rehearsal plan is ready. Keep the PR draft while any required choice, target-host test, recovery drill or capacity evidence is missing. The independent project review inspects the actual diff and evidence; merging requires a separate explicit owner decision.
