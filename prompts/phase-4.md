## Work

1. **Deployment and trust inventory.** Document the target topology, version-pinned images and upgrade path, exposed interfaces/TLS and network egress, runtime user/volume permissions, resource quotas, disk placement and capacity, and the identities that can read credentials or write inbox/outbox/config. Audit least privilege for API, publisher, fetcher, importer, database, operator and backup roles. Verify that production secret distribution avoids the development `./secrets` assumptions. Define and rehearse credential and Ed25519 signing-key rotation, including overlapping key windows, revocation, rollback and loss of the key; never commit a private key or raw token. The runbook's only documented database-password rotation is a `make reset` ("Reset and cleanup"), which deletes all data; define a rotation that keeps data. Rehearse with throwaway keys and tokens in tiers A–B. A production signing-key rotation applies only if the owner selects unattended online updates, and then waits for the custodian. A signed manifest is required for unattended publication; a provider's checksum alone is not authorization. Raw OSM Iran downloaded from a distributor is not a signed-manifest source. Manual publication needs no signing key: full-Iran snapshots arrive through the inbox or command line with a pinned or operator-authorized digest, unless the owner selects unattended online updates with a provider, signer and custodian. If an online source is selected, record its direct HTTPS reachability, or implement and test a constrained proxy path before relying on one.
2. **Bounded publication.** Investigate the missing whole-publication deadline noted when PR #6 was closed: `RunInbox` calls `ScanOnce` with its long-lived service context, and `runOsm2pgsql` uses `exec.CommandContext` without a process-group cancellation policy. It also reads osm2pgsql's output to EOF before `Wait`, so a descendant holding the pipe blocks the build even after osm2pgsql is killed. The publisher and importer containers run `karta` as PID 1 without an init (`compose.yaml` sets no `init`), so orphaned descendants are not reaped. Bound the whole job, from staging through validation and the switch, for inbox and online publication and for the command-line importer (or document why it is exempt). The pointer must still move only in a committed transaction. Make the deadline configurable, and make cancellation stop all importer descendants without hanging on inherited stdout. Give a timeout its own audited reason code. Define whether it counts toward `KARTA_PUBLISH_MAX_ATTEMPTS` or needs an explicit retry, so a snapshot that cannot finish within the budget does not loop. Preserve cleanup and audit on timeout/crash, keep the active release serving, and prove a later retry can proceed. Exercise an importer that forks a child which retains the output pipe (a test wrapper like `tests/integration/slow-osm2pgsql.sh`), a slow SQL/build phase and graceful shutdown within the Compose stop grace period, and check that no importer process remains afterwards. Set the production budget from tier D publication times plus a recorded margin; label any shipped default provisional. Do not copy PR #6 wholesale or assume its implementation is correct.
3. **Monitoring and response.** Supply deployable scrape/alert rules and a documented response for readiness, active release, API errors/latency, resource saturation, disk and WAL growth, publication duration/failures, fetcher state age and **active data age**. Today only the publisher's operator endpoint exports metrics. The public API has access logs but no request, error or latency metrics. Publication duration has no metric (only `karta_publication_in_progress` and submission states), and nothing exports PostgreSQL, WAL, container or host metrics. Add the missing signals without serving them on the public listener; pin any added exporter by digest and give it least privilege and no route out. Publisher-derived alerts go silent when the publisher stops, so also alert on a missing scrape target or series. A recent successful poll must not mark old data fresh. `KARTA_DATA_STALE_AFTER` is unset by default: take the threshold as a rule parameter, test with synthetic values, and make an unset threshold visible; the production value is an owner decision. Restrict the operator metrics endpoint with a scoped monitoring credential and TLS at any non-loopback exposure; avoid high-cardinality or sensitive labels. Test alert expressions against synthetic fresh/stale, paused and failed-source scenarios, and verify a stopped fetcher is observable.
4. **Backup and recovery.** No backup tooling exists yet. Define consistent backups for registry, release databases, required volumes/config and offline-held secrets, plus an explicit restore order. Decide and document whether backups hold release databases or the snapshots (with sidecar and manifest) needed to rebuild them, given the rebuild time measured in tier D. Protect backups and test restoring to a fresh host or isolated stack. Verify active pointer, retained/pinned releases, audit history, online anti-replay state/outbox, read-only serving, and key/token access after restore. Restoring an older registry also restores an older active pointer and an older `registry.source_state` serial. Audit the restored pointer like a rollback. Then either re-establish the anti-replay floor (for example from the fetcher state or the producer's current serial) or keep automatic online activation paused until an operator has checked it. Explain the behavior if fetcher state is lost or unreadable: never silently reset an undelivered verified serial. Establish and measure recovery time and data loss against owner targets. Rehearse database loss/corruption, disk exhaustion during import and normal serving, failed upgrade, rollback and cleanup in tiers A–B. Do not touch the owner's VM unless the owner chooses a tier C rehearsal and approves its plan.
5. **Capacity and fault rehearsal.** On the selected host with the full Iran snapshot (tier D), record hardware, Docker/PostGIS versions, PBF digest/provenance, configured concurrency, disk/RAM/CPU peak, import time, candidate/active/retained/pinned storage, API QPS and latency distribution, errors and availability under sustained map/search load. Include concurrent slow download/build/switch and pinned clients, network outage, restart and rollback. Derive an explicit capacity margin and safe thresholds from measurements. Iran needs its own region file: a box equal to the chosen snapshot's header or sidecar box (compared to 1e-7°), and acceptance checks (`min_counts`, `max_drop_fraction`, searches, tiles) derived from a measured Iran import, not invented or scaled from Chitgar. Several defaults were chosen before any full-Iran measurement: osm2pgsql cache 800 MB with 2 processes in non-slim mode, db 2 GiB and publisher 4 GiB, and `KARTA_RELEASE_STORAGE_BUDGET_MB` 10240 with candidate factor 40. Under those defaults, the candidate estimate alone for the 229,580,914-byte Iran file the sidecar claims is about 8.6 GiB. Re-derive these values from tier D measurements. Rehearse the same scenarios with Chitgar (tier B) first, and on the VM (tier C) only if the owner chooses it; report each tier separately. If traffic, availability, latency or update-lag objectives or the target host are undecided, measure provisional scenarios, label them, and keep the final gate open.
6. **License, documentation and acceptance.** Audit ODbL attribution and derivative-data obligations, bundled fonts and MapLibre licenses, third-party images/components and data provenance. Record the provenance chain of the Iran snapshot used in tier D (distributor or extraction, file, digest, replication sequence and timestamp), and mark each claim that could not be verified, as with the Chitgar sidecar's source digest. If release databases or backups leave the operator's control, raise the ODbL derivative-database question with the owner rather than deciding it. Update the runbook with exact bootstrap, upgrade, backup/restore, token/key rotation, monitoring, incident and rollback commands; keep OpenAPI and security documentation aligned with any behavior changes. Add meaningful unit/integration/fault tests for code changes and run existing race, static/security, fixture integration, browser, prefix and disconnected-network gates. Record commands, results and measured limits in the PR, each with its tier. A passing CI run alone does not satisfy Stage 4.
