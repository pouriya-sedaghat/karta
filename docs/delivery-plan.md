# Delivery and review plan

Every development stage ends in a reviewable pull request. Claude Code writes implementation and tests; the project review inspects the actual diff, checks integration behavior, asks for corrections if needed, and merges only after explicit owner decision. Review is keyed to PR creation/updates for this repository. Every stage must fully implement its bounded deliverable (security, validation, recovery, docs, and relevant negative cases included); a stub or single happy-path demo cannot pass. A future capability can be staged separately but must not be advertised as implemented beforehand. No service code or tests exist at the architecture-baseline stage.

| Stage | Deliverable | Acceptance evidence / review gate |
| --- | --- | --- |
| 0: baseline | Architecture, API outline, dependencies, assumptions, first implementation brief | Repository contains these documents; unresolved region/traffic decisions are visible. |
| 1: complete offline map and named-place search | Local PostGIS/osm2pgsql flex, complete basemap layer/style/font pipeline for agreed region, versioned and documented HTTP API, named-place/POI search including Persian names, minimal integration UI, small deterministic CI fixture **and** real Tehran smoke sample, reproducible runbook | With networking disabled after setup, manifest, search, tiles, all local assets and map demo work. Validate input limits, query safety, Unicode/RTL presentation, search ranking and empty/error responses, stable IDs, cache headers and release pinning contract. Run and record a real Chitgar extract check for roads, water and named places. Critical functionality cannot be a placeholder; if real-data acceptance is blocked, keep PR draft and state it. |
| 2: complete safe manual publication | Configurable inbox, full snapshot validation and provenance, isolated candidate, release registry, atomic activation, pinning, authenticated operator status/rollback, retention and cleanup | Serving continues while a snapshot is copied, imported or rejected. Truncated, malformed, duplicate, older, mismatched-region and symlinked input cannot corrupt active data. Crash/restart, concurrent uploads, pin expiry, rollback and disk exhaustion are exercised. No source is read until complete; all operator actions are audited. |
| 3: complete online updates and hybrid behavior | Configured HTTPS source polling and bounded download, digest/provenance, retries/backoff, shared validation and publication path, freshness metrics and operator policy | Newer compatible snapshot activates without stopping serving. Network loss, timeouts and corrupt downloads leave previous release healthy; local manual import works with no network. Simultaneous input sources have a deterministic priority/idempotency rule and recover across restarts. |
| 4: production deployment and capacity | Full documented operations, access control and secret rotation audit, observability/alerting, backups, recovery, resource limits, load/fault rehearsal | Demonstrated limits and capacity for selected region/QPS; backup/restore, disk exhaustion and rollback drill; license/attribution audit. A production-readiness claim requires the actual target environment and service objectives. |
| 5: Iran hybrid intake | A controlled source bridge for the selected raw-data distributor (Geofabrik's Iran extract): a downloader with the only route out, a network-less signer holding the key, read-only HTTPS serving, all feeding the Stage 3 online path; a protected local intake for outages: the authenticated `karta intake submit` command and an opt-in protected-folder watcher, with a narrow digest-authorization capability, an independent producer-side completion contract, a dedicated handoff directory, a switch-time re-check of every manual authorization, durable bridge serial recovery, bounded resources, monitoring and documentation ([ADR 0006](adr/0006-stage5-hybrid-intake.md)) | Engineering feature implemented and exercised with fixtures, a controlled HTTPS distributor stand-in and throwaway keys (tier A): incomplete, cut, changed, unsafe or mismatched deliveries are refused before any authorization; intake credentials reach nothing but their own authorizations; a revocation or expiry during a build leaves the release `ready` and the pointer unchanged, and a new authorization activates it without a rebuild; a rollback pauses unattended watcher activation but not a deliberate command; a removed credential is refused without a publisher restart; unchanged distributor hints download nothing; changed bytes with equal or older data are held; a lost or older signer state fails closed until an audited raise; the co-located fetcher reaches only the bridge. A **full-Iran measurement on the owner's VM is tier C** and a **production-host validation is tier D**: both need their own reviewed plans and deployment inputs, and neither is claimed by the implementation. |
| 6: optional extensions | Extract-compatible diff replication, address geocoding with self-hosted Nominatim, routing, HA | Separate ADR and benchmark for each; no implied MVP commitment. |

Review severity: blocker = active-release corruption, user-visible outage during a normal update, unsafe arbitrary file ingestion, security boundary breach, or runtime external dependency; major = API mismatch, failed rollback, absent test for a critical transition; minor = docs, ergonomics, and maintainability. A successful CI run alone is insufficient for a release claim.

Development geography: the provisional Chitgar Lake box in [development-data.md](development-data.md). Production geography (owner decision, recorded 2026-10-02): **Iran, from raw OSM data**; this fixes the data scope, not the snapshot source, an online-update provider or the host. Raw-data distributor (owner decision): Geofabrik's Iran extract, through the Stage 5 bridge or delivered locally; a matching region box does not prove Geofabrik origin. Open owner decisions: the fixed Iran PBF (exact bytes, digest, provenance) for the region file and any VM rehearsal, the bridge's production signing-key custodian and when a deployment enables online updates, which hosts may run the intake watcher and who may write their landing areas, whether every local delivery needs named-person attribution (hybrid inbox and online publication is a settled product requirement; manual submissions keep per-digest pinning or authorization, which the intake automates but does not remove), traffic/concurrency and availability/latency objectives, deployment environment and resource budget, backup and recovery objectives, network/TLS arrangement, whether search must include full addresses, and permitted update lag (acceptable active-data age). Defaults in code must be configurable until these are settled. Use measured Tehran import costs to inform, not determine, the production budget.
